# Web：BB 办公室减少重复绘制

## 定位与改动

借鉴 [fast-anything 0.8.0](https://github.com/EL4CTEO/fast-anything/tree/80ab099817b3d07ebe5b5221d4a9c6b881cfd044) 的「采样、改热点、验证、同机对照」流程。该项目不支持直接剖析 Godot 的 GDScript 或浏览器 WebGL，没有安装它的插件、移植到 Rust，也没有新增运行时依赖。这里使用 Godot 的绘制计数和 Chrome 实际运行的 Web 构建。

基线 `a8bc259` 中，BB 办公室的 `Props` 有 101 个可见网格、1,373 个材质表面；`Architecture` 有 14 个可见网格、52 个材质表面。这是场景清点，不是每帧绘制调用数。仅在 Web 的 BB 办公室，将相同网格、材质和渲染属性的可破坏物件，按 12 米空间单元组织成 `MultiMesh`。原模型的姿态、材质和碰撞体保留，破坏时隐藏对应实例，重开时恢复。房门、透明或多遍材质、独立交互物件不参与合批。未改变分辨率、材质或阴影设置；其他地图和原生版的渲染路径不变。

## Web 对照

Apple M6、Chrome 157、ANGLE Metal、60 Hz。桌面渲染为 1920×1080；触屏模拟为 844×390 CSS 视口、2532×1170 画布、1280×591 3D 渲染。每次运行完整 60 秒，使用相同出生点、镜头运动和自动开火。AI 和命中不会逐帧完全一致。普通阶段取 4–44.5 秒的样本；狂暴取 46–59.5 秒，排除入场、阶段切换和终场。

| 视口 / 阶段 | 每帧绘制调用中位数：前 → 后 | FPS：前 → 后 | P95 帧间隔：前 → 后 | 超过 33.334ms：前 → 后 |
| --- | ---: | ---: | ---: | ---: |
| 桌面 / 普通 | 2,516 → 1,609（−36%） | 59.88 → 60.00 | 18.1 → 17.6ms | 1 → 0 |
| 桌面 / 狂暴 | 2,530 → 1,617（−36%） | 59.92 → 60.00 | 17.5 → 17.4ms | 1 → 0 |
| 触屏模拟 / 普通 | 2,648 → 1,671（−37%） | 59.60 → 60.00 | 17.3 → 17.6ms | 2 → 0 |
| 触屏模拟 / 狂暴 | 2,765 → 1,625（−41%） | 58.60 → 60.00 | 16.9 → 18.1ms | 6 → 0 |

另一次触屏模拟使用 Chrome 4 倍 CPU 降速，依次运行基线、合批、合批、基线。四轮在相同 3D 尺寸下复现了绘制调用的下降。帧率和帧间隔受轮次波动，不能证明在低性能设备上会稳定提高帧率。

帧间隔包含 VSync 和系统调度，不是 GPU 耗时。未用实体手机或真实 120 Hz 设备测试。基准复现步骤见[开发说明](../development.md#web-rendering-benchmarks)。

## 回归验证

- Godot 4.7.2 导入、规则、场景导航、Web 帧预算和浏览器输入检查通过。
- BB 办公室回归在原生默认模式和 `--web-batches` 模式通过。用实际 Compatibility 渲染器检查了实例的材质与位置、单个物件消失不影响邻居、终场隐藏及重开恢复；碰撞、通路和房门亦保持原行为。
- 用固定镜头比较普通及狂暴各三个视角：六组对照的 PSNR 为 61.9–67.7 dB。不是逐像素相同，但保留了布置、色彩和光照效果。
- 本地正式 Web 导出通过包清单校验，未启用 `perfbench`。Chrome 在桌面入口实际开局并开火，在触屏入口开始沙城；均无浏览器控制台错误。这些是自动化检查，不是人工游玩。
