# 手机 Web 性能优化，2026-11-15

正式九图版本，基线 `e60721f`。在独立 main 工作树完成，未改动 space 月球基地分支。

## 结论与边界

主要问题是持续渲染开销：手机物理分辨率被当作完整 3D 分辨率，再叠加多重采样、环境遮蔽、敌人的多部件和重复边缘高光。提高帧率上限本身不能解决这些开销。办公室普通阶段从约 44.8 提高到 59.9 FPS，狂暴阶段约 32.2 提高到 59.2 FPS；沙城普通阶段的长帧明显减少。

这些是 Apple M5 / 桌面 Chrome 的同机对照，模拟手机的像素工作量，不是实体手机测试。未获得手机型号、浏览器、温控状态；未用真实 120Hz 设备测量。没有保证所有手机稳定 60 或 120 FPS。

## 对照方法

- 固定 CSS 844×390，手动设置基准构建的画布为 2532×1170，模拟 3 倍像素密度；浏览器实际 DPR 仍为 1。
- 同一出生点、镜头轻微周期转动，AI 正常移动，10 秒后持续按射速射击，自动装弹，自然进入 45 秒狂暴。各地图每个版本最终保留一轮完整 60 秒数据；动态 AI 和命中结果并非逐帧一致。
- 玩家在开始后设为无敌，避免死亡重生改变观察位置；没有冻结敌人或移除破坏物。普通阶段取 3 < elapsed < 44.5，狂暴阶段取 45 < elapsed < 59.5，剔除入场和终场。
- 报告的 frame time 是引擎连续帧的墙钟间隔，含 VSync 和系统调度，不是 GPU timer。CPU / physics 监视值约每秒更新，不能用于断言某一尖峰的精确 CPU 归因。
- 复测串行进行，未并行跑其他 GPU 压测。数据为单轮对照，不能把小幅差异当作统计保证。

## 实现

1. 移除 Web 固定 60 上限。使用浏览器 requestAnimationFrame 的稳定快速样本识别刷新率，达到 100Hz 时选择 120，否则选择 60；90Hz 设备目标为 60。匹配目标时交给浏览器 VSync，较高且不匹配的刷新率仍有帧率上限。背景页不采样，已识别的高刷新率不会因游戏降帧被重新判成 60。
2. 按物理画布限制 3D 渲染尺寸。移动端 60 目标：最长边 1280、像素预算 1280×720；120 目标：1024、1024×576。HUD 保持原画布分辨率。此次模拟由 2532×1170 缩至约 1280×591，3D 像素量减少约 74%。代价是手机远景细节更软，保留主视觉色彩、布局与玩法。
3. 加载时从 4 帧的偏快样本改为 16 帧 P75，并按 16.7 / 8.3ms 帧预算决定额外降档。战斗中不反复改渲染比例，以免重分配缓冲引起卡顿。移动端关闭屏幕空间环境遮蔽、限制阴影距离，Web 阴影纹理 2048；保留已有材质和烘焙细节。
4. 离线合并敌人装饰网格：步枪兵 50、突击兵 29 个网格都减少到 14，保留关节、碰撞逻辑、破甲和爆头部件。把材质颜色、粗糙度、金属度与发光信息编码到顶点和 UV，边缘高光合入主材质，减少 next_pass。突击兵受击闪白的独立覆盖材质保留。
5. 描边颜色边界强度为零时不再读四个邻近颜色纹理。加载遮罩下预热受击覆盖、球形碎片及狂暴灯光下的特效变体。
6. `?perf=1` 提供本地诊断读数及 DOM JSON，不发送遥测；普通入口无额外性能 UI。基准自动对战仅在 `perfbench` 自定义构建特性中启用，正式导出为空特性，不会自动开局或无敌。

沙城普通阶段 draw calls 中位数 1211 → 575，办公室 2963 → 2602。办公室仍有较多场景 draw calls，尚未对九张地图的静态环境做大规模合批。

## 剩余卡顿

改善不代表所有尖峰消失。办公室约 45.1 秒仍有 162.7ms 峰值，沙城狂暴仍有 56.5ms 单帧。入场前三秒也仍有首次资源提交的尖峰，单列在 `arrival.json`，未用普通阶段平均数掩盖。首次使用图形资源、灯光组合和系统调度可能贡献这些峰值；没有 GPU trace，不能声称已锁定唯一原因。

后续实体手机应优先记录 `?perf=1` 的普通 / 狂暴帧数据、设备和浏览器，再判断是进一步降低分辨率、减少静态场景提交，还是补齐首用资源预热。60Hz 测试不证明 120Hz 的 8.3ms 预算已满足。
